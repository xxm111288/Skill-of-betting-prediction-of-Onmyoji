# 阴阳师 · 对弈竞猜预测

把「界面上的两套面板 + 御魂」推演成「押哪边」。核心原则：**这是概率问题，不是玄学问题**；能算的算，算不出来的**如实说不确定**，禁止为了给出结论而编造依据。

## 运行环境

- **Python**：`scripts/simulate_duel.py` **只用标准库**，无第三方依赖。用环境里已有的 `python3`（Windows 上多为 `python`）；**不要写死某个绝对解释器路径**——先探测：
  ```bash
  python3 -V 2>/dev/null || python -V
  ```
  若存在虚拟环境（`<项目的>/.venv`）优先用它。
- **Shell**：优先用 **Bash** 工具；若该环境里 Bash 不可用（某些 Windows 环境会报 `dirname: command not found`），改用 **PowerShell** 工具，二者只需其一。
- **若 shell 不回显 stdout**（部分 Windows 环境如此）：让脚本自己把结果写文件（模拟器已内置 `--out`），再用 **Read** 工具读该文件；**避免用 `>` / `Out-File` 重定向生成待读文件**（部分环境产出 UTF-16，Read 会判为二进制）。
- 长任务（数据抓取、大样本模拟）用 `run_in_background`。

## 六步工作流

### 第 0 步：⭐ 先做式神名去歧义（**在索要/整理阵容之前就要做**）

**SP 阶式神以「修饰前缀 + 本体名」命名，裸名指的是本体（低阶）版本。**

- 「**追月神**」= **SR**（鬼火行动条引擎：`明月潮生` 先机推条 + `清辉月华` 全体攻速增益）
- 「**流光追月神**」= **SP**（照君/流光层数 + 集落光免扣火，**不是推条供火**）

两者**面板、技能、定位完全不同，认错等于整局判反**。同理：山兔(R)/梦寻山兔(SP)、座敷童子(R)/福悦座敷童子(SP)、大岳丸(SSR)/麓铭大岳丸(SP)、千姬(SSR)/鲸汐千姬(SP)……**全 51 组**。

- 查映射：`03A` §2 的「SP 变体 / sp_of」列，或 `data/shishen.json` 的 `sp_of`（SP→本体 id）/ `sp_forms`（本体→SP id）。
- **用户只写了裸名时**：按本体处理，**并在结论里显式声明**「按 SR 追月神算；若实际是 SP 流光追月神，结论会不同」。
- 详见 `01` §3.1、`references/intake.md` §0。

### 第 1 步：检查输入，缺就索要（不要猜）

**必须拿到的**：红/蓝双方各 5 个式神名（**写全名，先按第 0 步去歧义**）、每人的 8 项面板、佩御魂、以及**「阵容序号」**（决定群攻谁先挨打）。
**判定"信息够不够"**：缺任一项就算不完整。**不要用常识/记忆里的面板去补**——对弈面板由「百鬼弈加点器」生成，跟常规面板不是一回事（`01` §2.4）。

索要时**一次性给全清单**（模板见 `references/intake.md`），别一问一答挤牙膏。若用户只给了截图，**先把图里的数字逐项抄成表让用户确认**，再往下走。

### 第 2 步：整理成结构化的场次表

- 双方合计加成对比表（攻击/生命/防御/速度/暴击/暴伤/命中/抵抗），**先看速度与命中抵抗两行**。
- 每个式神一行：名称 / 8 项面板 / 御魂 / 阵容序号。
- **每个式神去知识库查一遍**：技能是什么、是否缺火、AI 在自动战斗下会不会用废（查 `03B` 技能原文 + `03_式神数据.md` 的 AI 风险点 + `06` §8 演员清单）。
- 存成 `lineup.json`（schema 见 `assets/lineup_template.json`），后面模拟要用。

### 第 3 步：按决策清单做初步判断

照 `01` §4 的六步走，每步写"打勾/打叉 + 理由"：

0. **鬼火与节奏**：数耗火 vs 供火；一速归属；`3 火拉条 + 3 火供火 + 2 火输出 = 8 火`。**对弈开局 4 火**（不是 3）。
1. **命中与控制链**：`命中率 = 基础概率 × (1+效果命中)` 再 `÷ (1+效果抵抗)`；多段按 `1−(1−p)^n`；对方有没有驱散/解除。
2. **输出与御魂契合**：是否满暴（`暴击 < 100%` 就要按 `1 + 暴击率×(暴伤−1)` 打折）；多段配针女 / 单段配破势；**警惕演员**。
3. **生存与容错**：治疗/护盾/复活/免死/反伤；**针女与控制类御魂打在护盾上不触发**。
   **三个必查项**（`04` §13–§14）：① **减疗只压「治疗」，压不住「恢复/吸血」**（千姬/匣中少女/鬼王酒吞的续航减疗无效）；
   ② **数清目标的免死次数**——免死**在扣血之前**结算，多数「每回目 1 次」，**石长姬 4 次、百羽凤凰火 3 次**，
   **茨木 `处决` 是官方写明的吸收/免疫/分摊穿透**；
   ③ **对面有分摊/保护（白藏主/椒图/薙魂/金鱼姬/毗沙门天）时，找「孤立」跳过全族，或改用间接伤害**（官方写明**无法分担**）。
   ④ 另查 **「失去生命」类效果**（荒骷髅/夜刀神/缚骨清姬/伊邪那美）：**不是伤害，护盾挡不住**。
4. **裁决之力**：**先估这局打几回合**——<5 回合只拼先手，>10 回合只拼斩杀与续航；第 11 回合起增伤翻倍。
5. **平局兜底**：存活数多者胜 → 再比剩余生命总和。
6. **写成决策**：推荐方 + 1–2 条最硬的理由 + 最大不确定性。

### 第 4 步：定性推演（说清"可能发生什么"）

写 3–5 条**情景**而不是一句结论，例如：
- 「蓝方一速+双拉 → 红方核心在前 2 回合被控/被秒 → 红方崩盘」
- 「红方蚌精开局全队护盾 → 蓝方针女+控制御魂首轮全部作废」
- 「拖到 12 回合后 → 蓝方治疗被裁决之力削到无效 → 红方靠茨木处决收场」

同时列出**关键杠杆**（速度差、命中 vs 抵抗、护盾有无、斩杀手段有无）与**方差来源**（未满暴、控制概率在 50% 附近、AI 乱放、同速随机）。

### 第 5 步：写 Python 脚本做蒙特卡洛

**直接复用**本 skill 的 `scripts/simulate_duel.py`，不要从零重写：

```bash
# 把 <skill> 换成 SKILL.md 所在目录；lineup.json 由第 2 步产出

# Windows 上把 python3 换成 python 即可
# 若该 shell 不回显 stdout，直接用 Read 工具读 sim_result.json（脚本已把完整结果写进去）
```

- 脚本已内置知识库公式、70 个御魂效果表、行动条/鬼火/裁决之力/平局兜底/群攻顺序（**只用标准库**）。
- 参数可调：`--trials`（默认 20000）、`--seed`、`--out`、`--sensitivity`、`--log`。
- **必须加 `--sensitivity`**：敏感性（谁一动就翻盘）比绝对胜率更有决策价值。
- **必须把 `assumptions[]` 原文抄进报告**，并声明这是**启发式比较模型，不是真值引擎**。

#### ⭐ 第 5 步的三个高危陷阱（都实际踩过，务必遵守）

**陷阱 1：漏建被动技能 —— 必须逐个 `grep` 原文，不能凭式神名想当然。**
一次实战里「天照」的复制伤害被动「无灭」**既没进 lineup 也没进未建模项**，
导致报告给出一个"看起来完整、实则漏了一个机制"的胜率。追问才发现还把三技能结构写错了
（把「3 段全体 + 追加 3 段指定」写成了「6 段单体」）。
→ **规矩**：每局至少对**双方全部 10 个式神**跑一遍 `grep` 技能的原始文本；
凡 `skill_type=4`（被动）或 `awaken_upgraded: true` 的条目，逐条确认"这局会不会触发"。
触发不了的要写明"为什么不触发"，**不能沉默略过**。

**⭐ 陷阱 1 的自救机制：把技能文案填进 `skills[].desc`，让脚本替你报警。**

模拟器**只读结构化参数**（`coef`/`hits`/`aoe`/`cd`…）。凡是**只有一段文字、没有数值**的
被动与特殊机制，在结构化输入里天然"不存在"，会被静默丢掉 —— 这正是上述「无灭」漏掉的原因。

R9 起 `simulate_duel.py` 内置了**被动守门**：只要把技能文案原文填进 `skills[].desc`
（或 unit 顶层的 `passive_desc` / `mechanics` / `notes`），脚本会自动扫描并输出两类告警：

| 告警 | 触发条件 | 处理 |
|---|---|---|
| `[机制未建模]` | 文案命中特殊机制关键词（时之隙 / 时之缝 / 时之辉 / 时寂之刻 / 布都御魂 / 玄血 / 形毁伤害 / 真实伤害 / 固定伤害 / 间接伤害 / 传导伤害 / 牺牲） | 必须逐条写进报告「未建模项」，并引用 `04` 对应章节 |
| `[被动未建模]` | 文案属被动/机制类（含「唯一效果 / 先机 / 印记 / 回合开始时 / 回合结束时 / 战斗开始时 / 阵亡时…」）**且不含任何数值** | 同上 |

**⭐ 陷阱 1 续：特殊机制「时之隙 / 玄血 / 布都御魂」—— 光看倍率必然误判。**

这些机制**在技能文案里往往只有效果描述、没有可代入的系数**，只靠倍率推演会得出相反结论：

| 机制 | 涉及式神 | 为什么容易误判 | 详见 |
|---|---|---|---|
| **时之隙族** | 卑弥呼(583)、时曜泷夜叉姬(584)、荒骷髅(585)、平将门(592) | 回合外行动**不推进鬼火条、不结算回合制冷却** → 有它的对局**鬼火节奏变慢**，长局利好低消耗阵容 | `04 §12.1` |
| **玄血 / 形毁伤害** | 龙珏(573) | 玄血**不是护盾**、是"另一种血条"；被攻击时受**形毁伤害（无视防御与减伤）** → 纯护盾/减伤流会被绕过 | `04 §12.2` |
| **布都御魂** | 平将门(592) | 攻击/防守架势自动切换 + 自回血 + 每强化 3 次进时之隙 → **单点爆发不易一波带走** | `04 §12.3` |

→ **规矩**：出现上述任一式神时，**必须**在报告里做定性修正，**不能只报模拟胜率**。

**⭐ 四种伤害类型必须分清（决定"打不打得动"）。**

`04 §7` 已给出完整对照表。报告里凡涉及这些式神，必须标明伤害类型：

- **直接伤害**（默认，无特殊标注）→ 吃防御、可暴击、触发双方御魂。
- **间接伤害** → **不触发双方御魂**、目标防御为 0 时必定暴击。
- **真实伤害**（荒骷髅 `黄泉战旗`）→ **无视防御**，可触发双方御魂，**不触发伤害来源被动**。
- **固定伤害**（平将门 `骄阳长明` 的 18%）→ **无视防御、不会暴击** → **堆暴伤对它无效**。

→ 常见错误：把「真实伤害」与「固定伤害」当同一种。两者都无视防御，但**御魂/被动/暴击行为不同**。

**陷阱 2：概率型触发（协战 / 追击 / 反击）不加门控会严重高估。**
以津真天「黄金羽」协战的原文是「**带黄金羽的敌方**被普攻时 50% 协战」。
第一版按"每次普攻都 roll 50%"实现，红方胜率直接从 22% 飙到 **60%** ——
因为红方缺火、一局要打 ~14 次普攻，等于白送 5 次满暴针女追击。
→ **规矩**：任何 `p` 型触发，先问"**触发条件是什么**"，把条件建成真实的**状态字段**（这里是 `feather > 0`），
再用 `--log` 跑单局看日志确认触发次数量级合理。**先看条件，再看概率。**

**陷阱 3：状态的"归属方"极易写反 —— 用单局日志验证。**
「黄金羽」是**初始挂在自己（以津真天）身上**、受击时把 1 层转给伤害来源；
我写成了"挂在伤害来源身上"，钩子判据写反（`owner is not victim` 应为 `owner is victim`），
结果整局"得羽"次数恒为 0。
→ **规矩**：涉及"谁的层数/状态转移给谁"的机制，**必须**用 `--log` 打印单局，肉眼确认层数在两个单位间正确流动过。
一次性写对几乎不可能。

#### ⭐ 改技能口径后，`ASSUMPTIONS` 必须同步改

`simulate_duel.py` 里的 `ASSUMPTIONS` 列表**就是报告"模型假设原文"章节的数据源**。
本次补建协战后，列表里那句「本模拟不建模：…协战…」没同步改，
导致报告一边说"已建模"、一边在假设原文里说"不建模"，**自相矛盾**。
→ 凡是新增/移除一个建模机制，**同一轮内**改 `ASSUMPTIONS`。

#### ⭐ 跑脚本前先确认 CLI（位置参数，不是 `--n`）

```bash
# 正确：lineup 是位置参数
python simulate_duel.py lineup.json --trials 20000 --seed 20260924 --out sim_result.json
# 错误：--n / --quiet 都不存在（会 exit 1 且不报错）
```
`sim_result.json` 是**两层**结构：顶层 `{assumptions, preflight, result, seed, trials, warnings}`，
胜负率在 **`result.win_rate = {red, blue, draw}`**，**不在顶层** —— 读错层级会得出"没有胜率字段"的错觉。

### 第 6 步：给胜率与推荐

输出**一段**结论：

- **胜率**：用模拟结果 + 定性修正给区间（如 `红 58%±6%`），并注明**这局属于哪一档**：
  - **高置信**（≥65% 或 ≤35%）→ 给明确推荐
  - **倾向**（55–65%）→ 给"倾向某方，建议中低额"
  - **五五开**（45–55%）→ **明确写"建议不压"**，并说明为什么
- **推荐押注方** + 理由（引用第 3 步的哪一条、模拟的哪个敏感性）。
- **最大不确定性**（通常来自 AI 行为与随机概率）+ **能翻盘的单一因素**。
- **不鼓励重注**；冷门追翻盘奖只做小额。
- **允许结论是"这局无法判断"**——这比强行给方向更有价值。

## 输出规范

报告写成 Markdown 文件（放用户工作区），结构固定：

1. 场次信息（时间/红蓝阵容/阵容序号）
2. 双方合计加成对比表
3. 逐式神速判表（面板 / 御魂 / 技能要点 / AI 风险）
4. 六步决策清单（打勾 + 理由）
5. 情景推演（3–5 条）+ 关键杠杆 + 方差来源
6. 模拟结果（胜率 / 平均回合 / 敏感性表 / 模型假设原文 / 未建模项）
   - **「未建模项」必须逐条抄录脚本输出的 `[被动未建模]` 与 `[机制未建模]` 告警**；
     无告警时写"本局无未建模被动/机制"，**不得整章省略**。
7. **结论：胜率区间 + 推荐方 + 最大不确定性**
8. 信源与求证记录

最后 `present_files` 交付（报告在前，脚本与 `sim_result.json` 在后）。

## 信息不全 / 有冲突时——必须联网求证

只有满足以下任一条件才停下来搜：① 知识库里该式神/御魂**标了 `⚠️ 待核实`**；② 知识库版本早于当前活动且你可能不知道新式神；③ 用户给的数值与知识库对不上。

- **信源优先级**：① `yys.163.com`（式神录/公告/攻略）＞ ② 网易大神 `ds.163.com`、NGA `bbs.nga.cn`、B 站实测 ＞ ③ 百科/内容站（**只作线索**）。
- **一个数值类结论要 ≥2 个独立信源、至少 1 个官方**，并记录链接与抓取日期。
- **已被判定为编造、禁止采信**：「11:00–13:00 场次最易爆冷」「带新皮肤 +15% 攻击」「系统凌晨 4 点重置胜率」「天命对弈玩法」「系统会标记 65% 稳赢局」以及一切"内部数据/离职策划爆料"。
- **⭐ 体验服 ≠ 正式服**：涉及「某机制在哪些玩法生效」时，**必须查最近一次官方维护公告**，体验服/测试服资料随时可能被推翻。
  典型例子：**「星痕御魂」**（八咫镜/天羽羽斩/月之石/纺缘锤/稻荷穗箭/预言星盘）在 2025-03 体验服标注「PVP 生效」，
  但 **2026-04-15 官方公告已把它们「调整为首领御魂」并明确「不再支持斗技、结界突破、道馆玩法」** → **对弈竞猜同样不生效**。
  网上仍大量流传旧说法，**不要采信**。正确做法：搜 `阴阳师 <年月>日维护更新公告` 找官方原文。
- **查不到就写「未找到可靠信源，待核实」**，绝不用旧版本数值或推测填补。
- 顺手把新核实到的内容**回写进知识库**（增量修订 + 在文末「变更记录」加一行），不要只在对话里说。

## 禁止事项

- ❌ 用户没给全信息就开算 → 先索要。
- ❌ 用知识库里的"典型面板"替代用户实际面板。
- ❌ 只报一个胜率数字而不给假设与不确定性。
- ❌ 把模拟器说成"官方引擎/精确预测"。
- ❌ 鼓励重注或暗示"稳赢"。
- ❌ 编造式神技能、御魂数值、活动规则。
- ❌ **混淆本体与 SP**（写「追月神」却按 SP 流光追月神算，或反之）→ 先做第 0 步去歧义。
- ❌ **把「只有文字、没有参数」的被动当作不存在** → 必须填入 `skills[].desc` 让脚本告警，并写进「未建模项」。
- ❌ **把「真实伤害」与「固定伤害」混为一谈** → 两者都无视防御，但御魂/被动/暴击行为不同（见 `04 §7.1`）。
